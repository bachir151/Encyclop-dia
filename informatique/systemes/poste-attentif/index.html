Un poste qui sait
quand agir.

Martine quitte son bureau. Un radar le détecte, Windows protège sa session, puis installe un logiciel au bon moment. Comment relier ces actions sans confondre capteur, serveur et programme ?

01 · LE PROBLÈME

Quel problème cherchait-on à résoudre ?

Martine accueille du public. Elle consulte des dossiers sur son ordinateur, lit parfois un document papier, puis se lève pour chercher une pièce. Windows voit les frappes au clavier et les mouvements de souris. Il ne sait pas directement si la chaise est occupée.

Deux situations produisent donc le même signal informatique : Martine lit sans toucher le clavier et Martine a quitté le bureau. L’inactivité des entrées ne suffit pas à les distinguer. Un verrouillage après dix minutes protège à terme, mais laisse un délai d’exposition après le départ. Dix minutes est ici une hypothèse de maquette, pas une règle universelle.

Besoin principal

Réduire le délai pendant lequel une session reste accessible après le départ. Le verrouillage manuel reste une bonne habitude ; le boîtier apporte une protection complémentaire.

Besoin secondaire

Éviter de démarrer les installations au milieu du travail de Martine. Une absence confirmée devient une condition supplémentaire, mais ne garantit pas la durée de disponibilité future.

Reconstruisons la solution

  1. Pour connaître une présence physique, il faut une mesure du monde physique : un capteur.
  2. Pour transmettre cette mesure au PC, il faut un programme embarqué et une liaison.
  3. Pour verrouiller ou installer, il faut un programme Windows disposant des droits adaptés.
  4. Pour gérer plusieurs postes, il faut centraliser les paramètres et les résultats techniques.

Prérequis : distinguer un fichier d’un programme, savoir qu’une adresse IP identifie une interface et qu’un serveur répond à des demandes. Les termes nouveaux sont définis dans la suite.

02 · DE LA PRÉSENCE AU MESSAGE

Qu’y a-t-il dans le boîtier ?

Vue fonctionnelle : ce dessin n’est pas un plan de câblage broche par broche.

Le radar LD2410 : mesurer, sans filmer

Le radar émet une onde autour de 24 GHz et analyse les échos. Le constructeur décrit une détection des personnes en mouvement et des micro-mouvements de personnes immobiles. La respiration peut modifier l’écho ; ce n’est ni une photographie ni une identification de la personne. Le traitement FMCW exploite une émission dont la fréquence varie pour estimer notamment la distance [1].

À 24 GHz, la longueur d’onde vaut environ λ = c / f = 12,5 mm. Cela aide à comprendre pourquoi de petits déplacements modifient le signal. La portée utile, les seuils et le comportement sous un bureau se vérifient sur le module acheté. La distance annoncée par le fabricant n’est pas une garantie de distinction entre deux personnes proches.

L’ESP32 : lire, traiter, transmettre

Un microcontrôleur est un petit ordinateur spécialisé. Son programme, écrit ici en C++ avec l’environnement Arduino, lit les messages du radar, commande la LED et construit les messages vers Windows. Son Wi-Fi et son Bluetooth ne sont pas nécessaires à cette architecture USB.

Le radar dialogue avec l’ESP32 en UART : des bits circulent successivement sur les fils TX et RX. Le TX de l’un va vers le RX de l’autre, avec une masse GND commune. Les broches, niveaux logiques et alimentations doivent être vérifiés sur les versions exactes des modules. Une alimentation USB 5 V ne signifie pas que tous les signaux acceptent 5 V.

La LED : rendre la décision visible

Une LED RVB combine trois couleurs. Nous choisissons vert pour la présence, orange pour l’avertissement et rouge pour un verrouillage demandé ou une anomalie signalée, avec un texte explicatif côté PC. Des résistances adaptées limitent le courant. La couleur seule n’est pas une preuve de verrouillage : le programme doit vérifier l’état réel de la session.

Le boîtier plastique et sa fixation sont aussi importants que le code : changer l’orientation du radar peut changer les détections. Un second ESP32 peut servir à la démonstration du faux boîtier.

03 · DEUX PC, UN RÉSEAU

Comment les éléments sont-ils connectés ?

La version retenue fonctionne avec Windows 11 Famille, sans domaine Active Directory. Un PC Ubuntu héberge les services serveur, directement ou dans une VM Ubuntu Server. Une seule VM serveur suffit ; Windows Server a été retiré de cette adaptation.

Une VM est un ordinateur logiciel

Le logiciel de virtualisation réserve à Ubuntu Server de la mémoire, un disque virtuel et une carte réseau virtuelle. En mode pont, cette carte rejoint le réseau physique par l’interface Ethernet de l’hôte. Le poste Windows peut contacter l’adresse de la VM directement. Ce mode est proposé pour la maquette ; le logiciel de virtualisation reste à choisir.

Le trajet est : carte virtuelle de la VM → pont de l’hôte → carte Ethernet physique → switch → PC Windows. Deux machines du même sous-réseau n’ont pas besoin d’un routeur pour ces échanges locaux. Si le serveur tourne directement sur l’hôte, on utilise l’adresse de l’hôte et on supprime l’étape VM.

04 · DU FICHIER AU LOGICIEL

Samba, MSI, PowerShell : qui fait quoi ?

Pour installer un logiciel chez Martine, trois problèmes sont distincts : disposer du paquet, le transporter et l’exécuter.

  1. Le MSI est le paquet. C’est un fichier contenant des ressources et des instructions pour Windows Installer. On pourrait aussi le transporter sur une clé USB.
  2. Samba partage le dossier. Installé sur Ubuntu, il rend les fichiers accessibles à Windows par le protocole SMB [2]. Ici, Samba est utilisé comme serveur de fichiers, pas comme contrôleur de domaine.
  3. Le script PowerShell coordonne. Écrit par l’étudiant, il choisit le paquet autorisé, le copie, le vérifie et attend les conditions prévues.
  4. Windows Installer réalise l’installation. Le script lance l’outil msiexec qui interprète le MSI [3].
Une clé USB remplacée par le réseau. L’analogie explique le transport, mais le partage ajoute des comptes, des permissions et un protocole. Samba n’envoie pas spontanément un logiciel à installer.

Pourquoi copier avant d’installer ?

Une fois le paquet local et validé, une coupure du partage ne coupe pas sa lecture pendant l’installation. Le cache doit être protégé contre les modifications par un utilisateur ordinaire. Les fichiers ne deviennent pas fiables uniquement parce qu’ils sont locaux.

# Illustration de l’appel, à tester avec un paquet approuvé :
msiexec /i "C:\ProgramData\PosteAttentif\Cache\logiciel-test.msi" /quiet /norestart

/quiet supprime l’interface de l’installateur et /norestart évite le redémarrage automatique demandé par Windows Installer. Cela ne garantit pas qu’un paquet quelconque ne perturbera jamais une application. On sélectionne des MSI de test et on vérifie leur comportement. Le programme doit traiter le code de retour, dont le cas « installation réussie, redémarrage nécessaire ».

Le compte local de Martine est standard. Le composant de maintenance possède les privilèges nécessaires ; ses identifiants d’accès SMB sont configurés explicitement. Sans domaine, le compte SYSTÈME n’a pas magiquement un accès authentifié à Samba.

05 · LE FICHIER NE DIT PAS QUAND L’INSTALLER

Pourquoi faut-il aussi une API Python ?

Samba sait fournir un fichier. Mais un dossier ne répond pas, à lui seul, à « quel logiciel manque sur ce poste ? », « la maintenance est-elle autorisée ? » et « l’installation a-t-elle réussi ? ».

On écrit donc une application en Python. FastAPI aide à définir une API : des adresses auxquelles un autre programme peut envoyer une demande structurée [4]. PowerShell est un client de cette API. Le serveur n’exécute pas le MSI à distance : le poste reste responsable de l’action locale.

Ordre pédagogique simplifié : une copie anticipée peut être faite avant l’absence. Les décisions de présence restent sur le PC.

JSON : une fiche de paramètres lisible

JSON est un format texte qui associe des noms à des valeurs. Voici une configuration fictive ; les noms des champs sont une proposition d’implémentation.

{
  "version": 3,
  "absence_confirmation_s": 10,
  "avertissement_s": 3,
  "maintenance_apres_s": 1200,
  "maintenance_autorisee": true
}

Le poste récupère cette fiche par HTTPS, vérifie le certificat du serveur, son format et les bornes autorisées, puis conserve la dernière version valide. Une valeur négative ou un délai déraisonnable est rejeté. Le serveur ne fournit jamais une commande libre à exécuter : les actions possibles sont programmées à l’avance.

SQLite : garder une mémoire technique

L’API conserve les résultats dans une base SQLite. Ce moteur est intégré à l’application et stocke les données dans un fichier, sans serveur de base distinct [5]. Les PC parlent à l’API, jamais directement au fichier SQLite et jamais en le modifiant sur Samba.

Une ligne peut contenir un identifiant de poste fictif, un paquet, sa version, un résultat et un jour. Le technicien voit ensuite dans son navigateur les installations réussies, les erreurs et les reports. Les événements réessayés après une panne doivent posséder un identifiant unique pour éviter les doublons.

Configuration centralisée ≠ Active Directory. Le serveur distribue les paramètres de notre application. Il ne crée pas de domaine, n’authentifie pas les ouvertures de session Windows et n’applique pas de véritables GPO.
06 · L’ADAPTATION WINDOWS FAMILLE

Que remplace-t-on, et que garde-t-on ?

Windows 11 Famille ne rejoint pas un domaine Active Directory. L’édition Pro ajoute cette capacité [6]. Remplacer Windows Server par un contrôleur de domaine Samba ne supprimerait pas la limite du client Famille. Notre adaptation évite donc le domaine.

Architecture initialeAdaptation retenue
Compte de domaineCompte Windows local standard pour Martine
GPO du domaineParamètres limités de l’application, récupérés sur Ubuntu
Verrouillage de secours par GPOÉcran de veille local avec reprise exigeant la connexion, à configurer et tester
Authentification SMB du domaineCompte Samba dédié, avec lecture seule des paquets
VM Windows ServerSupprimée ; serveur Ubuntu conservé

Deux niveaux de protection

Le radar peut déclencher un verrouillage rapide. Indépendamment, Windows garde un verrouillage local après inactivité, par exemple avec un écran de veille et l’option de reprise sur l’écran de connexion [7]. Ce mécanisme doit être testé même si le programme de présence est arrêté. Un simple écran éteint ne prouve pas que la session est verrouillée.

Conséquence assumée : Martine peut encore être verrouillée après une longue lecture sans clavier, même si le radar la voit. On ne simule pas des mouvements de souris pour neutraliser ce filet de sécurité. Une configuration locale n’offre pas la même gouvernance qu’une GPO ; sa résistance à la modification doit être vérifiée avec le compte standard choisi.

Un programme privilégié n’est pas la session utilisateur

Le composant de fond lit l’USB et coordonne la maintenance. Un petit composant dans la session utilisateur peut demander le verrouillage et afficher les avertissements. Le canal entre eux doit être restreint. L’API Windows LockWorkStation s’appelle depuis le bureau interactif ; un simple appel depuis un service SYSTÈME ne suffit pas à garantir le verrouillage [8].

Un script PowerShell ne devient pas un service Windows parce qu’on le lance. Il faut définir son lancement, sa supervision, ses droits et sa reprise après panne. Les tâches planifiées et le journal d’événements peuvent aider ; la solution précise reste à prototyper.

07 · UN SCÉNARIO COMPLET

Une matinée avec Martine

Avancez étape par étape. Les horaires illustrent le fonctionnement attendu ; ils ne décrivent ni une personne réelle ni une installation déjà réalisée.

9 h 00 · Elle se connecte

Martine utilise son compte local Windows. Le programme récupère une configuration valide et la liste des paquets autorisés. Le radar indique une présence. La LED verte rend cet état visible.

9 h 05 · Elle lit

Le radar détecte une présence même sans frappe au clavier. Le programme ne demande pas de verrouillage pour absence. Le verrouillage Windows sur inactivité continue néanmoins de fonctionner.

9 h 12 · Elle se lève

Le programme exige dix secondes d’absence continue puis affiche trois secondes d’avertissement orange. Si Martine revient avant la fin, l’action est annulée. Ces durées sont des exemples réglables.

9 h 12 min 13 s · Session protégée

Si l’absence est confirmée, Windows verrouille la session. Les documents restent ouverts. Un retour devant le radar ne déverrouille jamais la session : Martine doit s’authentifier elle-même.

9 h 32 · Maintenance possible

Après vingt minutes d’absence continue, le programme peut démarrer un MSI approuvé et vérifié, si l’application concernée est fermée et si la maintenance est autorisée. Un retard de capteur ou une anomalie interdit ce démarrage.

9 h 33 · Martine revient trop tôt

Aucune nouvelle installation ne démarre. Celle déjà engagée n’est pas brutalement interrompue : seuls des paquets préalablement testés comme non perturbateurs sont retenus. Le programme ne ferme aucun travail et ne redémarre pas le PC.

Le technicien consulte le bilan

L’API reçoit « paquet de test installé sur PC-01 », avec le jour. Les heures de départ et de retour ne sont pas envoyées. Si le serveur était indisponible, les résultats techniques sont conservés temporairement puis réessayés.

  1. Connexion locale et récupération de la configuration.
  2. Lecture : présence détectée, filet de sécurité local conservé.
  3. Départ : confirmation puis avertissement.
  4. Verrouillage, sans déverrouillage automatique au retour.
  5. Absence longue : installation sous conditions.
  6. Retour : aucun nouveau paquet, pas d’interruption brutale.

    09 · FAIRE CONFIANCE, MAIS À QUOI ?

    Trois protections pour trois problèmes

    1. HMAC : le message vient-il du bon boîtier ?

    Un faux ESP32 peut affirmer « présent » en permanence. Le vrai boîtier et le PC partagent donc une clé secrète. Un HMAC calcule un code d’authentification à partir du message et de cette clé [9]. Ici, on retient HMAC-SHA256. Le PC recalcule le code et le compare.

    Le message inclut aussi un compteur et un identifiant de session issu d’un nouveau défi au raccordement. Le PC refuse un compteur déjà vu et les messages d’une ancienne session. HMAC seul n’empêche pas le rejeu, et il ne chiffre pas les données. L’enrôlement initial doit se faire dans un contexte contrôlé, avec autorisation locale et appui physique ; la clé ne doit pas apparaître dans les journaux ou dans Git.

    Ce qui est protégé

    L’origine et l’intégrité des messages, dans la limite de la protection de la clé.

    Ce qui ne l’est pas

    La justesse du radar, l’identité de la personne et une extraction physique du secret sur un montage non durci.

    2. HTTPS et comptes : qui peut demander quoi ?

    HTTPS protège les échanges avec l’API si le certificat est vérifié. Un jeton propre à chaque poste permet d’autoriser ses opérations ; il est distinct de la clé HMAC du boîtier. Le tableau de bord exige une authentification. Le compte Samba permet seulement de lire les paquets ; les agents ne peuvent pas les remplacer.

    3. Empreinte : le paquet reçu est-il celui attendu ?

    PowerShell calcule SHA-256 sur le fichier local et compare au manifeste reçu par un canal de confiance. L’empreinte vérifie la correspondance ; une empreinte fournie à côté d’un fichier tous deux modifiables par un attaquant ne suffit pas. Une signature de l’éditeur peut compléter cette vérification.

    En panne, « inconnu » ne veut pas dire « absent »

    Un boîtier débranché, une preuve invalide ou un message trop ancien donnent l’état inconnu. La proposition retenue est alors : signaler l’anomalie, interdire de démarrer une maintenance, et demander un verrouillage après une courte temporisation. Le filet local reste indépendant. Un faux boîtier peut provoquer une indisponibilité, mais ne doit pas obtenir le droit de lancer une installation.

    Si Ubuntu est inaccessible, la protection locale continue avec la dernière configuration valide. Par prudence, la maquette ne démarre pas de nouvelle installation tant que le serveur est indisponible ; un MSI déjà lancé se termine selon sa politique. Les résultats sont réémis plus tard.

    Vie privée : limiter les données, pas seulement les noms

    Aucune caméra et aucune remontée des heures de présence. Les états physiques restent volatils sur le poste, sans historique permanent dans le fonctionnement normal. Les journaux de mise au point doivent être séparés et purgés. Les résultats techniques sont datés au jour ; même ainsi, un identifiant de PC peut être rattachable à une personne. La minimisation ne rend donc pas automatiquement toutes les données anonymes.

    Problème de transfert : le serveur est coupé après la copie du MSI

    Le verrouillage local doit continuer. Le MSI présent dans le cache ne suffit pas à autoriser son démarrage : notre politique prudente exige le serveur disponible pour une nouvelle installation. Une installation déjà lancée se termine sans interruption brutale et son résultat attend le retour du serveur. Une autre politique hors ligne serait possible, mais devrait être explicitement conçue et testée.
