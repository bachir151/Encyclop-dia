Laboratoire DHCP : comprendre, attaquer, défendre

Quatre TP reproductibles sur un Victus Debian, deux Raspberry Pi et un switch Ethernet. Observer les paquets, identifier les vulnérabilités et expérimenter les protections.

Condition impérative : travailler sur un switch ou VLAN de test sans liaison vers la box, le Wi-Fi domestique, le lycée ou Internet pendant les expériences. Utiliser une interface Ethernet dédiée : ne pas désactiver à distance les services de ton PC. Les adresses ci-dessous sont fictives et réservées au laboratoire.
TP 01DHCP et DORADécouvrir les quatre messages et la notion de bail.TP 02Rogue DHCPObserver deux serveurs concurrents.TP 03Starvation contrôléeÉpuiser trois baux avec trois clients de laboratoire.TP 04DHCP SnoopingBloquer le faux serveur avec un switch compatible.

Avant de commencer

Matériel : Victus, Pi 1, Pi 2, switch, trois câbles Ethernet. Installer au besoin dnsmasq, tcpdump, dhclient (paquet isc-dhcp-client selon distribution) et Wireshark. Effectuer les installations avant d'isoler le laboratoire.

Repérer l'interface Ethernet de chaque appareil :

ip -br link
ip -br addr

Dans toutes les commandes, remplacer ETH par le nom réel de l'interface Ethernet de test, par exemple enp3s0 ou eth0. Les commandes supposent une installation de dnsmasq gérée par systemd et peuvent nécessiter une adaptation.

Plan IP : Victus 192.168.50.1/24, Pi 2 (gestion) 192.168.50.2/24, pool initial .100–.105, Pi 1 client automatique. Aucun routeur ni DNS réel n'est nécessaire pour joindre le Victus.

TP 01 · LES PREMIERS PRINCIPES

Comment un ordinateur obtient-il une adresse ?

Objectif : observer Discover → Offer → Request → ACK et déterminer qui attribue une IP, pourquoi un bail expire et comment vérifier la communication.

1. Configurer le Victus

sudo ip addr add 192.168.50.1/24 dev ETH
sudo ip link set ETH up
sudo tee /etc/dnsmasq.d/lab-dhcp.conf >/dev/null <<'EOF'
interface=ETH
bind-interfaces
port=0
dhcp-range=192.168.50.100,192.168.50.105,255.255.255.0,10m
log-dhcp
EOF
sudo dnsmasq --test
sudo systemctl restart dnsmasq

Si 192.168.50.1 existe déjà sur l'interface, ne pas la dupliquer. Si le port UDP 67 est occupé, identifier le processus avec sudo ss -lunp et corriger sur l'interface du labo, sans arrêter aveuglément le gestionnaire réseau.

2. Capturer sur Pi 1

sudo tcpdump -ni ETH -vvv 'udp port 67 or udp port 68'
# Dans un second terminal, après installation de dhclient :
sudo dhclient -v ETH
ip -4 addr show dev ETH
ping -c 3 192.168.50.1

Un client possédant déjà un bail peut ne pas envoyer Discover : utiliser une interface de test sans bail ou supprimer seulement les baux de laboratoire. Filtre Wireshark : bootp ou dhcp selon version.

3. Analyse

MessageRôle
DISCOVERLe client cherche des serveurs.
OFFERUn serveur propose une configuration.
REQUESTLe client demande une proposition précise.
ACKLe serveur confirme l'attribution.
Questions à expliquer

Pourquoi le premier message peut-il être diffusé ? Quelle différence entre adresse proposée et adresse attribuée ? Que peut faire un PC si aucun serveur ne répond ? À quoi sert le bail ?

TP 02 · FAUX SERVEUR

Rogue DHCP : à quel serveur faire confiance ?

Objectif : faire apparaître deux offres DHCP, identifier le serveur retenu et constater la conséquence d'une mauvaise configuration DNS ou passerelle. Aucune interception de trafic Internet n'est réalisée.

1. Laisser actif le DHCP légitime

Conserver le Victus et son pool 192.168.50.100–105 du TP 1. Sur Pi 2, utiliser une IP fixe pour la gestion :

sudo ip addr add 192.168.50.2/24 dev ETH
sudo ip link set ETH up

2. Lancer un deuxième DHCP sur Pi 2

sudo tee /etc/dnsmasq.d/lab-dhcp.conf >/dev/null <<'EOF'
interface=ETH
bind-interfaces
port=0
dhcp-range=192.168.50.200,192.168.50.205,255.255.255.0,10m
dhcp-option=option:dns-server,192.168.50.2
dhcp-option=option:router,192.168.50.2
log-dhcp
EOF
sudo dnsmasq --test
sudo systemctl restart dnsmasq

3. Capturer puis comparer

sudo tcpdump -ni ETH -vvv 'udp port 67 or udp port 68'
# Sur le Pi 1, renouveler depuis un client sans bail valide :
ip -4 addr show dev ETH
ip route
resolvectl status  # si systemd-resolved est présent

Repérer dans les offres l'option 54 (identifiant du serveur). Le client n'accepte pas nécessairement la première offre : son comportement dépend de l'implémentation et des baux précédents. Le Pi 2 n'étant ni une vraie passerelle ni un résolveur DNS, un accès extérieur peut échouer ; cela ne démontre pas à lui seul une interception.

4. Restaurer

# Sur Pi 2 :
sudo systemctl stop dnsmasq
# Renouveler ensuite le bail DHCP du Pi 1.
Questions à expliquer

Comment prouver quel serveur a été choisi ? Un mauvais DNS peut-il nuire sans changer le masque IP ? Pourquoi deux offres ne signifient-elles pas automatiquement une attaque réussie ?

TP 03 · DISPONIBILITÉ

DHCP Starvation : le pool peut-il être épuisé ?

Objectif : simuler trois identités clientes distinctes qui occupent un pool de trois adresses, puis observer ce que reçoit un quatrième client. Pas de flood, pas de rafale de trames forgées.

1. Limiter le pool du Victus à trois adresses

Après arrêt du DHCP sur Pi 2, remplacer dans /etc/dnsmasq.d/lab-dhcp.conf la plage par :

dhcp-range=192.168.50.100,192.168.50.102,255.255.255.0,10m
# Puis vérifier et redémarrer :
sudo dnsmasq --test && sudo systemctl restart dnsmasq

Réinitialiser uniquement les baux de test si nécessaire, jamais un serveur de production.

2. Créer trois interfaces clientes sur Pi 2

Option didactique : trois machines virtuelles sur un pont de test isolé. Autre option : interfaces macvlan, dont chaque MAC distincte peut demander son propre bail. Cette option dépend de la configuration du réseau et du gestionnaire d'interfaces :

for i in 1 2 3; do
  sudo ip link add lab$i link ETH type macvlan mode bridge
  sudo ip link set lab$i address 02:00:00:50:00:0$i
  sudo ip link set lab$i up
done
for i in 1 2 3; do
  sudo dhclient -4 -v -pf /run/dhclient-lab$i.pid \
    -lf /tmp/dhclient-lab$i.leases lab$i
done

3. Vérifier les baux

# Sur Victus :
sudo cat /var/lib/misc/dnsmasq.leases
sudo journalctl -u dnsmasq -n 60 --no-pager
# Sur Pi 1 : démarrer une demande DHCP sans bail valide
sudo tcpdump -ni ETH -vvv 'udp port 67 or udp port 68'

Vérifier le nombre de baux effectivement attribués ; trois requêtes n'impliquent pas nécessairement trois réservations. Si le pool est plein, Pi 1 peut ne recevoir aucune offre utilisable. Selon le client, il peut adopter ultérieurement une adresse IPv4 link-local (169.254/16).

4. Nettoyer les interfaces et restaurer le pool

# Sur Pi 2 :
for i in 1 2 3; do
  sudo dhclient -r -pf /run/dhclient-lab$i.pid lab$i 2>/dev/null || true
  sudo ip link delete lab$i
done
# Sur Victus : rétablir .100 à .105, vérifier, redémarrer.
Questions à expliquer

Pourquoi trois MAC distinctes suffisent-elles ici ? Quelles limites cette simulation a-t-elle par rapport à une attaque réelle ? Un rate limiting suffit-il contre une saturation lente ?

TP 04 · DÉFENSE

DHCP Snooping : distinguer ports fiables et non fiables

Objectif : empêcher les offres DHCP provenant de Pi 2 tout en autorisant celles du Victus, si le switch prend en charge DHCP Snooping.

Port de testMachinePolitique
P1Victus / DHCP légitimeTrusted
P2Pi 1 / clientUntrusted
P3Pi 2 / faux serveurUntrusted

1. Identifier le switch

Noter constructeur, modèle, firmware, VLAN de test et numéros de ports. Vérifier dans sa documentation la disponibilité de DHCP Snooping, la syntaxe exacte et la procédure de sauvegarde. Une commande Cisco ne doit pas être copiée sur un HP ProCurve sans vérification.

2. Définir puis appliquer la politique

Activer DHCP Snooping uniquement sur le VLAN de laboratoire. Marquer le port du Victus trusted ; conserver les ports des Pi untrusted. Ne pas marquer tous les ports comme fiables.

3. Refaire la capture du TP 2

Remettre temporairement en service les deux DHCP, relancer une acquisition neuve sur Pi 1 et examiner les offres. L'offre provenant de Pi 2 ne doit pas franchir le switch, alors que celle du serveur légitime doit arriver. Consulter les compteurs du switch si disponibles.

4. Comprendre la portée de la protection

DHCP Snooping vise les réponses de serveurs non autorisés. L'épuisement du pool peut nécessiter d'autres mécanismes : contrôle d'accès, limitation, supervision et segmentation. Un débit plafonné ne garantit pas à lui seul la prévention d'une saturation progressive.

Si le switch ne propose pas DHCP Snooping, faire une étude comparative documentée, plutôt que de supposer une protection inexistante.

Questions à expliquer

Pourquoi P1 est-il trusted ? Quel paquet le switch doit-il bloquer ? Pourquoi DHCP Snooping et anti-starvation ne sont-ils pas synonymes ?

Critères de réussite et remise en état

  1. Captures annotées : DORA ; deux offres ; absence d'offre lorsque le pool est effectivement occupé ; filtrage par switch si compatible.
  2. Journal des hypothèses : mécanisme observé, preuve, limite, résultat attendu et résultat obtenu.
  3. Arrêter le dnsmasq de test sur Pi 2, effacer les interfaces macvlan de test, restaurer la configuration du Victus et les réglages réseau initiaux.
  4. Ne reconnecter le laboratoire au réseau domestique qu'après désactivation de tous les serveurs DHCP expérimentaux.

Références techniques : RFC 2131 (DHCP, Droms, 1997) ; RFC 2132 (options DHCP, Alexander et Droms, 1997) ; RFC 3927 (IPv4 link-local, Cheshire, Aboba et Guttman, 2005) ; documentation officielle dnsmasq et documentation du constructeur du switch.
